# Правила работы в репозитории

## Git workflow

1. Перед началом задачи проверьте `git status --short`; не включайте в работу несвязанные изменения.
2. После реализации обновите относящуюся к задаче документацию и выполните релевантные проверки.
3. Когда изменения готовы, добавьте только файлы в scope задачи в stage и покажите пользователю `git status`, staged `git diff --stat` и список staged файлов.
4. Не создавайте commit, не изменяйте опубликованную историю и не выполняйте push без явного одобрения пользователя. После одобренного commit покажите hash и снова дождитесь отдельного одобрения перед push.
5. Не меняйте remote, ветку по умолчанию, `.gitignore` или Git-конфигурацию без явной задачи или согласования с пользователем.

## Инженерные правила

1. Перед изменениями прочитайте `README.md` и относящиеся к задаче документы из `docs/`.
2. Не меняйте архитектуру молча: зафиксируйте существенное решение в `docs/DECISIONS.md` и обновите затронутую документацию.
3. Не добавляйте зависимости без необходимости; предпочтительны стандартные возможности текущего стека.
4. Не используйте `any` без документированного обоснования. Сохраняйте строгую типизацию на границах API и домена.
5. После изменений выполняйте релевантные `pnpm lint`, `pnpm typecheck` и тесты. Не заявляйте об их прохождении, если не запускали.
6. Никогда не удаляйте и не переписывайте применённые миграции. Для изменения схемы создайте новую миграцию.
7. Не ослабляйте проверку Telegram `initData`, RBAC, контроль доступа к PII или rate limiting ради скорости реализации.
8. Реализуйте только функции, входящие в текущую задачу. Не добавляйте чат, платежи, AI matching или adult-контент без отдельного решения.
9. Сохраняйте обратную совместимость REST API или явно документируйте breaking change, версию API и план миграции клиентов.
10. Храните даты в UTC, не коммитьте секреты, не логируйте `initData`, токены или контактные данные.
