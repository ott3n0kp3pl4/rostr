# Журнал архитектурных решений

## ADR-001 — модульный Next.js-монолит

**Статус:** принято, 2026-07-22.
**Решение:** один Next.js App Router проект с REST route handlers и выделенными серверными модулями.
**Причина:** MVP выигрывает от единого контракта, меньшей операционной нагрузки и быстрой валидации домена.
**Последствие:** нельзя помещать доменные правила в компоненты или handlers; при росте API/воркеров модуль можно вынести в отдельный сервис.

## ADR-002 — PostgreSQL и Prisma, Redis отложен

**Статус:** принято, 2026-07-22.
**Решение:** PostgreSQL — source of truth, Prisma — ORM; Redis не включён.
**Причина:** текущим требованиям не нужна отдельная очередь или распределённый cache; это снижает локальную сложность.
**Последствие:** добавить Redis можно только с конкретным кейсом (rate limits/outbox/cache) и отдельным ADR.

## ADR-003 — privacy by default

**Статус:** принято, 2026-07-22.
**Решение:** контакты отделены от публичного профиля и выдаются только policy-guarded disclosure.
**Причина:** защита кандидатов и предотвращение массового сбора — центральное требование.
**Последствие:** DTO и логи обязаны иметь PII allowlist; приглашение/отклик не считаются неявным согласием.

## ADR-004 — проверка Telegram только на сервере

**Статус:** принято, 2026-07-22.
**Решение:** raw `initData` проверяется HMAC и по сроку действия серверным bot token.
**Причина:** `initDataUnsafe` может быть подделан.
**Последствие:** локальный режим ограничен UI; production без bot token не обслуживает аутентификацию.

## ADR-005 — роли через permissions и scope

**Статус:** принято, 2026-07-22.
**Решение:** роли — данные, проверки осуществляются permissions с global/agency scope.
**Причина:** новые роли/команды агентств не должны вести к переписыванию условий.
**Последствие:** каждый метод обязан определить нужное permission и предметный scope.

## ADR-006 — onboarding сохраняется по шагам и не доверяет client user ID

**Статус:** принято, 2026-07-23.
**Решение:** каждый выбор wizard отправляет один типизированный action в `/api/v1/onboarding`; actor определяется сервером по проверенному Telegram `initData`. В development разрешён только один фиксированный local actor при явном `TELEGRAM_DEV_MODE=true`.
**Причина:** пользователь может безопасно продолжить прерванный сценарий, а API нельзя направить на произвольный `user_id`.
**Последствие:** до появления сессий `initData` передаётся в body каждого onboarding-запроса и нигде не логируется; повторный запуск для разработки доступен только через закрытый dev-reset endpoint.
